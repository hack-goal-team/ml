# Общий пайплайн обучения

Для запуска на временной VM в Yandex Cloud см. [cloud/README.md](cloud/README.md).

Эта папка — самостоятельная точка повторного обучения модели на исходных и новых данных. Добавьте новые журналы событий в `data/incoming_events/` и запустите один скрипт: он объединит все записи, сформирует признаки, заново разобьёт устройства на train/val/test, выполнит feature selection, Optuna-тюнинг, обучит итоговую модель и посчитает метрики.

Шаблоны в `notebooks/` — копии исходных тетрадок. Они **не перезаписываются**. Для каждого прогона скрипт создаёт рабочие копии в `artifacts/runs/<run_id>/notebooks/` и только там подставляет найденные годы и реально доступные чанки. По умолчанию feature selection и подбор параметров используют ограниченные выборки, а итоговая модель обучается на всех полученных train-чанках. Validation и test остаются отдельными выборками для оценки качества; финальная оценка охватывает все test-файлы.

Результат зависит от фактически переданных файлов, настроек и версии кода; пример из репозитория не заменяет полный набор событий. Скрипт не заменяет модель сервиса инференса.

## Состав

| Путь | Назначение |
| --- | --- |
| `config.yaml` | Пути к данным, kernel и лимиты чанков. |
| `notebooks/` | Неизменяемые шаблоны пяти этапов обучения. |
| `data/incoming_events/` | Сюда складывать исходные и новые журналы событий `.parquet`. |
| `data/reference/` | Справочники датчиков, объектов и погодный CSV. |
| `run_pipeline.py` | Единая команда полного обучения. |
| `artifacts/runs/` | Результаты независимых запусков. |

## Быстрый старт

Перейдите в папку пайплайна и установите зависимости в нужное Python-окружение:

```bash
cd retraining
python -m pip install -r requirements.txt
python run_pipeline.py
```

Результат появится в новом каталоге `artifacts/runs/YYYYMMDD_HHMMSS/`:

- `survival_optuna/best_model.cbm` — итоговая CatBoost-модель;
- `survival_optuna/scores_final.csv` — PR-AUC на validation и test;
- `survival_optuna/best_params.json` — найденные параметры;
- `notebooks/` — фактически выполненные тетрадки с выводами;
- `data/` — точный снимок данных, использованных в этом запуске.

Для фиксированного имени прогона используйте `python run_pipeline.py --run-id <уникальный-id>`. Если каталог с таким именем уже существует, скрипт завершится с ошибкой и не перезапишет артефакты.

## Как добавить новые данные

1. Скопируйте один или несколько parquet-файлов в `data/incoming_events/`. Скрипт читает только файлы по `input.events_glob` из `config.yaml` (по умолчанию `*.parquet`); записи одного года объединяются. Для полного прогона положите журналы в отдельный каталог и укажите его в `input.events_dir`, либо настройте `input.events_glob`, чтобы исключить `журнал_событий_пример.parquet`. Не удаляйте старые реальные файлы, если они тоже должны остаться в обучающей выборке.
2. Убедитесь, что у каждого файла есть колонки: `ид_события`, `ид_канала_данных`, `дата`, `время`, `значение_датчика`, `тревожное`.
3. При изменении справочников или погоды замените соответствующий файл в `data/reference/` либо поменяйте путь в `config.yaml`.
4. Запустите `python run_pipeline.py`.

В репозитории уже лежит минимальный пример: `журнал_событий_пример.parquet` и все три обязательных справочника. Он показывает формат. Для полноценного обучения нужны данные с достаточным числом разных каналов и наблюдений; маленький пример может не дать достаточно данных для каждого train/val/test-сплита.

## Конфигурация

В `config.yaml` можно изменить каталоги данных, Jupyter kernel, таймаут и число чанков для этапов feature selection, tuning и final training. Значение `all` у `final_training.train_chunks` и `final_training.val_chunks` означает все доступные чанки соответствующего сплита. Целочисленные лимиты автоматически ограничиваются числом существующих чанков. На test лимит не действует: финальный ноутбук оценивает все test-файлы. При нуле чанков этап завершится ошибкой.

Новые данные должны быть в том же формате, что и пример. Дата должна приводиться к календарной дате; погодный CSV должен содержать колонку `time` и погодные поля из исходной тетрадки.

## Фактическое использование чанков

| Этап | Train | Validation | Test |
| --- | --- | --- | --- |
| Отбор признаков | До 4 чанков | До 20 чанков | До 20 чанков |
| Подбор параметров | До 8 чанков | До 80 чанков | До 20 чанков в шаблоне |
| Итоговое обучение | Все (`final_training.train_chunks: all`) | Все (`final_training.val_chunks: all`) | Все `chunk_*.parquet` для итоговой оценки |

Числа заданы в `notebook_limits` и ограничиваются фактическим количеством файлов. Итоговый ноутбук берёт лимиты train/val из секции `final_training`; если её нет в конфиге, используются лимиты `tuning`. Все test-файлы читаются в итоговой оценке пакетами. Test не используется для обучения итоговой модели, но ноутбук отбора признаков считает `test_pr_auc` по кандидатам. Поэтому итоговую test-метрику нельзя считать оценкой на полностью закрытой выборке.

## Проверка результата

Прогон считается завершённым после успешного выхода `run_pipeline.py` и проверки `best_model.cbm`, `scores_final.csv`, `best_params.json` и выполненных ноутбуков в одном каталоге запуска. В выводе последнего ноутбука сверяйте число найденных test-файлов с входным набором. Для сравнения с прежней моделью и правилами «тревога вчера» и «не менее десяти тревог вчера» используйте `compare_old_model.py` и `baseline_previous_day.py` — они считают метрики на тех же test-строках и горизонте прогноза. Автоматической выкладки модели нет.

Для воспроизводимости фиксируйте commit, `config.yaml`, перечень Parquet и их SHA-256, число train/val/test-чанков и итоговые артефакты. Данные и секреты размещайте вне Git, если они не предназначены для публикации.
